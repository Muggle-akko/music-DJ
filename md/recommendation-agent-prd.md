# Awudio 推荐系统 V2：供开发 Agent 执行的 PRD

> 后续决定：内置 V1 已移除，内置推荐统一 V2；外部 Agent 模式以 [外部 Agent PRD](external-agent-mode-prd.md) 为准。本文件保留 V2 初次设计背景。

状态：工程实现已接入、本地试用中；连续收听与个人体验验收尚未完成。详见 [实施与验收记录](./recommendation-v2-implementation.md)。
日期：2026-10-16。代码基线：`3e8f56c`。
适用范围：当前本地、单用户 Awudio，继续使用 Node 服务、网易云适配服务、现有 DeepSeek/OpenAI 配置。
本文是下一轮推荐改造的实施依据；旧文档 `ai-recommendation-design.md` 只作 V1 历史参考。若冲突，以本文的 V2 目标为准。

## 1. 要解决的核心问题

用户希望电台既懂自己的收藏，又能从网易云发现合适的歌，并随着真实收听反馈改善。模型应能基于工具返回的真实歌曲做决策，而不是仅产出“睡前、轻松、爵士”等搜索文字，或编歌名后碰运气搜索。

采用“受限推荐 Agent + 确定性推荐内核”：

1. Agent 理解这一次听歌任务，选择召回工具、种子和搜索方向。
2. 服务端执行白名单工具，建立有来源、有真实歌曲 ID 的候选池。
3. 程序过滤硬约束并粗排；Agent 只能在候选池中选择 ID、分阶段编排和提出有限补查。
4. 程序验证结果、去重、检查完整播放资格、补位，最终才交给播放器。
5. 推荐曝光、实际播放和主观反馈分别记录，形成可重放的反馈闭环。

第一版不使用自由循环 Agent，不引入向量数据库或额外 Agent 框架。模型是否支持原生 tool calling 不影响实现：可用严格 JSON action 协议，由服务端执行和回传结果。

## 2. 已有能力与确认的问题

以下来自本地代码审查；网易云接口“存在模块”不等于本次已验证线上可用。

| 项目 | 当前事实 / 问题 | 代码证据与处理方向 |
|---|---|---|
| 意图解析 | 已有规则路由、AI 路由、复杂需求规划，不是纯聊天程序 | `server.mjs`: `resolveIntentRoute`、`createAiBackedRecommendationPlan`；复用接口，避免多套提示词重复改写同一意图 |
| 歌曲来源 | 已有收藏、相似歌曲、日推、歌曲搜索、主题歌单搜索 | `resolveProfileRecommendedTracks`、`resolveSearchRecommendedTracks`、`resolvePlaylistSearchTracks`；统一进入候选池，不再各路自行选完后直接拼接 |
| 固定收藏比例 | 普通画像路径使用 `PROFILE_RECOMMENDATION_LIKED_RATIO=0.72`；多阶段路径单独从收藏分阶段挑选 | 缺少统一的新鲜度目标；专题、探索、多阶段应使用同一选择内核 |
| 画像缺失 | 审查时 `data/listening-profile.json` 不存在；画像主路径直接依赖 `allLikedSongs` | 页面能浏览网易云收藏不等于已建立推荐画像；必须有可观测、可重试的同步入口 |
| 特征污染 | 蒸馏脚本把用户所有歌单名称信号的前两项追加到每首收藏歌曲 | `inferTrackStyleTags`；例如“爵士歌单”不能让全部歌曲成为爵士，必须区分用户偏好、歌单语境、歌曲事实 |
| 特征失真 | 歌名文字推测语言；关键词推测风格；没有可靠 BPM、音频能量或人声检测 | `detectTextFamily`、`scoreMoodFit`；标注推断来源和置信度，不宣传成音频理解 |
| 打分不平衡 | 周播放次数线性乘 5，多关键词可重复加分；天气、周末、年代存在固定映射 | `scoreProfileSong`、`buildRecommendationScene`；做特征归一化，显式要求优先于默认场景 |
| 反馈含义混淆 | 队列删除与取消喜欢都发 `remove`，服务端作为较强负反馈；开始播放和恢复播放均可触发 `play` | `public/app.js`: `removeQueueItem`、`removeLikedTrack`、audio `play` 监听；必须拆分事件并去重 |
| 缺少有效收听证据 | 没有累计实际收听时长；`complete` 主要来自自然结束，默认单曲循环时提前返回 | `sendTaste`、`handleEnded`；不能用开始播放代表喜欢，或用跳到结尾代表听完 |
| 场景错绑风险 | 反馈可能从 `state.now` 推断情绪；该字段会在生成推荐时写入，不等于真正播放曲目 | `createDjChatResponse`、`buildFeedbackScene`；反馈绑定实际播放会话的场景快照 |
| 播放资格 | `getSongUrlDetails` 只保留 URL 等部分字段，没有传递试听信息；URL 存在即视为可播 | 区分完整、试听、受限、未知，避免把试听当完整歌曲 |
| 存储并发 | 已有原子写文件及部分保护合并，但多个业务先读再改仍需审计 | `writeState`、`mergeProtectedStateForWrite`；必须测试“生成中点喜欢”不会被旧快照覆盖 |

当前本地事件量很少，不能据此声称已学到稳定偏好。旧说明中的产品愿景也不能当作已实现能力。

## 3. 产品目标、范围与成功定义

### 3.1 本轮必须交付

- 完整收藏元数据的可靠同步及覆盖率说明；画像缺失时仍能使用真实来源推荐。
- Agent 能执行有限检索，基于真实候选 ID 选歌；所有行为有 trace 可解释。
- 同一套内核支持随便听、熟悉优先、发现新歌、指定歌曲/歌手、严格主题、多阶段需求。
- 把“喜欢 / 不喜欢 / 暂时不合适 / 删除 / 取消喜欢 / 听过”分开。
- 稳定的可播放结果、明确的不足说明、对照评测、可回滚开关。

### 3.2 本轮不做

手机远程访问、云部署、多用户、自动操作网易云红心、离线下载、音频 embedding、真实 BPM/调性分析、无缝混音、开放式联网研究。保留现有主持人展示与语音管线，本轮不重做声音系统。

### 3.3 成功定义

- 工程正确性：约束、真实 ID、播放资格、反馈归因均可自动验证。
- 推荐体验：同一批真实请求上，用户认为比 V1 更贴合且更愿意继续听；不是“调用了更多工具”就算改善。
- 必须分开报告：离线测试、真实网易云联调、真实连续收听。没有实测的指标标注未验证。

## 4. 交互与意图契约

沿用现有 AI 电台入口和 `/api/chat`、`/api/chat/stream`。推荐算法升级不重排整个界面。

| 输入举例 | 行为 |
|---|---|
| “来点适合现在听的” | 默认均衡模式；没有明确场景时，只把时间作为弱信号，不把深夜自动等同于助眠 |
| “今天只想听熟歌” | familiar；只从同步收藏和有可靠正反馈的已知曲目召回 |
| “别总是收藏里的，发现点新的” | discovery；提高非收藏歌曲占比，保留用户口味锚点 |
| “只要纯音乐，不要爵士” | 显式硬约束；未知是否有人声的候选不能冒充已满足“只要纯音乐” |
| “来一期某歌手，包含这两首，不要 Live” | 确认歌手实体，优先精确命中两首；全单不得混入 Live，找不到要说明 |
| “写半小时代码，然后放松 15 分钟” | 按实际曲长分配两个阶段；不强行凑满 15 首 |
| “这首现在不适合，但我挺喜欢的” | 本次场景负反馈，保留长期喜欢 |
| “为什么给我这首？” | 读取对应推荐 trace 回答，不发新推荐、不改队列 |
| “下一首 / 暂停” | 播放控制沿用现有机制，不启动召回、不生成新歌单 |

优先级：明确禁止与权限限制 > 本次明确点歌和主题 > 当前阶段要求 > 本次探索偏好 > 长期偏好 > 时间/天气弱信号。

遇到“只要纯音乐 + 点一首已知人声歌”等不可同时满足的要求，不静默取舍：保留现有队列，返回简短冲突说明和选择建议。明确点了一首被本地屏蔽的歌时，提示冲突；只有明确“这次仍然播放”才可做一次性覆盖，不自动解除长期屏蔽。

计数规则：普通推荐沿用 2–5 首；整期无数量/时长要求默认 24 首，上限 30 首。明确数量 1–30 首按要求执行；按时长请求可少于 15 首。超过上限要说明本次上限，不能悄悄截断。数量与时长冲突时，明确数量为硬目标、时长为软目标，并报告实际时长。

## 5. 数据与画像

### 5.1 同步流程

新增内部 `ProfileSyncService`，CLI 与本地 UI 共用：

1. 校验登录，解析当前用户 ID；只同步自己的数据。
2. 分页读取用户歌单，定位收藏歌单；分页取得完整收藏元数据，必要时批量补歌曲详情。
3. 保存歌手 ID、专辑 ID、原始版本信息、时长、收藏添加时间与明确来源。
4. `/user/record` 的历史/周榜只作为接口返回的截断样本，缺失播放次数为 `null`，不是 0 次。
5. 曲风百科按需、增量补充；先让基础画像可用，不等待整库逐首百科请求。
6. 单首失败不毁整批；主列表同步失败不覆盖上次成功快照。部分成功保留已有记录，标记覆盖率，只有完整成功快照才推断取消收藏。
7. 歌曲级标签只来自该歌曲或其实际所属歌单；用户全部歌单名称只能作为用户级弱兴趣。
8. 写入原子快照，记录 `accountKey`、同步时间、总量、已取数量、失败来源及 schemaVersion。切换账号必须隔离画像、缓存、反馈。

本地入口：提供“同步网易云偏好”按钮和同步结果（例如“已同步 n/m 首，播放记录为部分样本”）；不要求用户手动操作 JSON。避免每次推荐全量同步；默认快照超过 24 小时标记可更新，用户触发同步。首次缺失可启动一次后台同步，当前请求走冷启动路径，不阻塞等待全量结果。

增量仍须检测收藏删除；百科过期按 30 天补查。上述 TTL 是初始配置值，不是上游数据保证。同步任务单实例运行、可重试，保留最后成功快照。

### 5.2 特征结构（目标契约）

```json
{
  "provider": "netease",
  "id": "真实歌曲ID",
  "title": "上游歌名",
  "artistIds": ["真实歌手ID"],
  "artists": ["上游歌手名"],
  "albumId": "真实专辑ID",
  "durationMs": 240000,
  "version": {"kind": "studio", "confidence": 0.9, "source": "title+metadata"},
  "features": {
    "genre": [{"value": "jazz", "source": "song_wiki", "confidence": 0.8}],
    "vocal": {"value": "unknown", "confidence": 0},
    "energy": {"value": null, "confidence": 0},
    "language": {"value": null, "confidence": 0}
  },
  "membership": {"inLikedLibrary": true, "playlistIds": []},
  "provenance": [{"source": "liked_library", "retrievedAt": "ISO时间"}]
}
```

ID 始终用字符串；未知字段保留 unknown/null。置信度是本系统的启发式可信度，不是测量准确率。歌名字形不等于演唱语言，歌单标签不等于逐首音频事实。没有可靠证据不生成 BPM、人声间奏或“我听见了某种乐器”等结论。

长期画像与当前会话分离：长期来自收藏、明确正反馈和持续有效收听；当前会话由本次指令、阶段、最近跳过及“现在不合适”驱动。默认天气不参与硬过滤；不主动新增定位或天气服务。

## 6. 推荐 Agent 与执行协议

### 6.1 固定执行流程

```text
请求 + 偏好摘要 + 实际播放上下文
  -> IntentPlan（含硬/软约束、实体、阶段、探索模式）
  -> Agent 提交召回动作 -> 服务端校验并执行工具
  -> 候选合并 / 补齐元数据 / 硬过滤 / 可解释粗排
  -> Agent 在最多 80 个候选内选择 ID 和编排，可请求一次补查
  -> 程序验证、有限补位、完整播放资格检查
  -> 最终曲目 + 简短理由 + trace
  -> 主持人串词作为后置可选步骤
```

工具可以一轮并行调用，工具之间有依赖时分批执行。默认两次模型调用：规划与召回决策一次、基于真实候选选曲一次。可选一次补查后的重排，总计最多三次；无效 JSON 最多修复一次，所有模型请求合计最多四次。工具补查只能一轮；禁止“继续找直到满意”的无界循环。

`IntentPlan` 至少包含：`intent`、`queueAction`（none/cards/replace/append）、`requestedCount`、`targetDurationMs`、`mode`、`requestedEntities`、`hardConstraints`、`softPreferences`、`stages`、`voiceRequested`。规则锁定明确数字/否定词，模型不能悄悄覆盖。普通“推荐几首”默认 cards，只有明确生成整期/换一批整期或点击生成歌单才 replace；“接着来几首”默认 append。

硬约束用结构化项 `{field,operator,value,origin,evidenceRequired}` 表达，例如 `version not_in [live]`、`artistId in [...]`、`vocal eq instrumental`。字段、操作符和枚举值需做白名单校验，保留原始请求片段用于核对。识别有歧义时不能把模型低置信度猜测升级成硬约束；先简短确认或作为带说明的软偏好。

### 6.2 工具白名单

下表是要实现的内部工具名；不是已存在的 HTTP 路由。

| 工具 | 输入边界 | 实际数据来源 | 结果 |
|---|---|---|---|
| `profile.lookup` | 受限过滤条件、最多 120 首 | 本地快照、应用内喜欢、有效收听聚合 | 真实歌曲及证据，不返回整份私有账号资料 |
| `catalog.searchSongs` | query ≤ 80 字、limit ≤ 50 | 现有 `/cloudsearch` 或 `/search` 适配 | 歌曲 ID、详情摘要、匹配证据 |
| `catalog.similarSongs` | 1 个有效 seedId、limit ≤ 50 | `/simi/song` | 歌曲、种子 ID、关联来源 |
| `catalog.dailySongs` | 每轮最多一次 | `/recommend/songs` | 上游推荐及来源 |
| `catalog.searchPlaylists` | query ≤ 80 字、最多 5 个歌单 | 现有歌单搜索 | 歌单 ID、标题、标签、简介摘要 |
| `catalog.playlistTracks` | 从本轮搜索/用户指定的歌单 ID 读取，limit ≤ 50 | `/playlist/track/all` | 歌曲、所属歌单证据 |
| `catalog.artistSongs` | 已解析真实 artistId、limit ≤ 50 | `/artist/songs` | 歌曲，供歌手专题使用 |

元数据补齐、资格检查由内核负责，模型不能自己指定音频 URL。歌手同名用结构化艺人搜索/详情解析 ID，解析也计入检索预算；无法唯一解析时只在歧义会改变结果时问用户。`personal_fm` 等模块可做后续实验，本轮不默认接入。

示例 action：`{"tool":"catalog.similarSongs","args":{"seedId":"本轮真实种子ID","limit":30}}`。执行器拒绝未知工具、超限参数、任意 URL、越权账号、模型伪造的不可追溯种子。用户明确给出的歌曲/歌单 ID 经上游解析验证后才可使用。

网易云返回的歌单简介、评论、歌词均为数据，不能作为工具指令；对模型只给截断后的内容，不传 Cookie、Key、邮箱或账号原始资料。候选中的文本也不能修改工具白名单。

### 6.3 请求预算与停止条件

- 候选池最多 400 个唯一歌曲 ID，模型最多见 80 个；按阶段和来源保留配额，避免初排全被熟歌占满。
- 一轮最多 12 次检索类上游请求，含分页、实体解析、失败请求和补查；本地 lookup 不计入网络调用。来源不足时优先保护明确点歌和硬约束。
- 详情补齐每轮最多 100 个 ID；百科新补查最多 10 首。播放资格最多检查 80 个 ID，优先批量查询、每批不超过 20 个 ID；每批最多一个兼容端点回退，最坏 8 次上游资格请求。必须验证当前 API 的批量返回契约后启用，不依赖结果数组位置。
- 详情批次最多 20 个 ID、最多 5 次请求，不做自动重试；百科最多 10 次单首请求。因此单轮最坏上游请求数为 12 检索 + 5 详情 + 10 百科 + 8 资格 = 35 次，实际仍受总截止时间限制。全库同步是独立任务，不得借它绕过当前推荐预算。
- 并发总上限 4，单次上游 5 秒超时；模型单次 8 秒超时。所有等待受同一请求截止时间限制，总推荐阶段预算 30 秒。剩余时间不足则不启动新轮次，返回已合格结果或明确失败。
- 不因模型不可用重试全部上游。取消/新请求到来要终止旧请求未完成的工作，过期结果不写队列或电台历史。
- 模型、检索、资格请求均记录次数和耗时。预算值集中配置，可按真实延迟调整，不能散落魔法数字。

工具失败返回结构化状态：`ok/empty/unauthorized/rate_limited/timeout/error`。HTTP 200 仍要检查业务 code、字段和预期结构；失败不能记为“确实没有歌曲”。

## 7. 候选召回、评分与编排

### 7.1 来源与新鲜度是两个维度

召回源是收藏、相似、日推、搜索和歌单；熟悉程度按歌曲与用户的关系判断。同一首歌从多个源出现只保留一个实体，追加 provenance，不能冒充多首或重复获得全部来源加分。

默认均衡初始配额：熟悉 55%、相邻探索 35%、较远探索 10%；发现模式 20/60/20；熟悉模式 100/0/0。这些是候选足够时的软目标，取整误差最多 1 首；明确点歌、硬约束、完整可播优先。各类别：

- 熟悉：在成功同步的收藏库内，或有应用内明确喜欢/可靠有效收听证据。
- 相邻探索：不属于熟悉，且有真实相似种子、已知歌手或可靠风格关联。
- 较远探索：不属于前两类，但仍有满足请求的主题/风格证据。

“非收藏”不等于“一生没听过”。同步不完整时熟悉程度标 unknown，不用它承诺新歌比例。用户说“只要新歌”默认解释为当前已知收藏/收听记录外；用户明确最近发行则解析为发行日期约束，缺少日期不得冒充新发行。

没有本地画像时：本轮明确歌曲/歌手做种子；其次应用内喜欢；再用已登录日推与主题搜索。不把演示曲目混入真实结果。不无条件请求所有来源：熟悉模式优先本地；严格歌手/主题以专题来源为主；探索模式至少尝试一条真实探索来源，有来源失败则披露不足。

### 7.2 硬过滤

先执行确定性过滤，再让模型选择。禁止名单、明确歌手/版本/语言/人声约束、无效 ID、不可完整播放在最终结果中不可被模型放宽。metadata unknown 是否通过取决于约束：明确“只要 X”须有足够证据；软偏好可接纳 unknown 但不能解释成已验证。

默认去重只合并相同 ID，及有同歌手/专辑/别名等充分证据的同曲不同版本；不能仅凭同名排除不同歌手的不同作品。Live、remix、翻唱保留版本信息，用户明确要版本时不能归并错歌。“比较不同版本”可覆盖版本去重，但不能产生相同 ID 重复。

当前正在播放及尚未播放的队列曲目不重复加入 append 结果；replace 可替换旧待播队列，但默认避开当前曲目和本次播放会话已听曲。近 2 小时实际有效播放歌曲默认排除，明确重听可覆盖；更早重复用时间衰减惩罚。候选不足先放宽来源比例/歌手间隔，再放宽非本会话的重复软偏好，必须记录，不放宽明确禁止。

### 7.3 可解释粗排

所有分量归一化到 0–1，权重集中在配置中。第一版基线：

```text
base = 0.35 * requestFit
     + 0.25 * tasteAffinity
     + 0.15 * sceneFit
     + 0.10 * freshnessFit
     + 0.10 * sourceConfidence
     + 0.05 * sessionPositive
     - repeatPenalty - contextNegativePenalty
```

实现必须保存每项分值和 evidence：

- `requestFit`：明确实体、主题、版本匹配，不是把每个同义关键词重复累加。
- `tasteAffinity`：收藏/明确喜欢、歌手关联、可靠标签；历史/周播放样本采用 `log1p` 加上限，缺失中性，不能线性压倒请求。
- `sceneFit`：本次实际阶段和可靠特征；没有证据时中性，不用“下雨必爵士”补事实。
- `freshnessFit`：相对于本次模式与已知曝光/播放，不奖励不可验证的“没听过”。
- `sourceConfidence`：来源可信度与证据完整性，不简单按来源个数累加。
- `sessionPositive`：同场景显式认可及有效收听；只开始播放为 0。
- 惩罚均有上限和时间衰减；模型无法重排掉硬排除结果。

无观测的中性值设 0.5；显式反证设低值，不能把缺失等同于反证。每项需有固定测试样例。保存 V1 排序与 V2 基线结果，先比较确定性改造，再评估 Agent 重排的增益。

初始分值映射固定如下，后续调参需递增 policyVersion：

- `requestFit/sceneFit`：已满足硬约束后，软条件逐项打分：有直接证据为 `0.5 + 0.5 * confidence`，反证为 `0.5 - 0.5 * confidence`，未知为 0.5，再按条件权重取平均；没有对应软条件为 0.5。同义词归为同一条件，只计一次。
- `tasteAffinity`：显式喜欢/收藏 0.9；有可靠有效收听 0.75；达到了跨曲目证据门槛的偏好歌手 0.7；只有可靠偏好风格 0.6；无证据 0.5。采用最高一档，再以有上限的历史播放样本微调最多 ±0.05，不把多路同源证据累加。
- `freshnessFit`：近 7 天没有曝光/收听记录为 1，有曝光未起播为 0.7，有有效收听为 0.2；历史覆盖未知为 0.5。熟悉模式该项固定 0.5。类别配额另行控制，不能拿此分数当作“绝对未听过”的证据。
- `sourceConfidence`：可信歌曲级元数据 0.9；真实相似关联/实际所属歌单主题 0.7；只有搜索命中 0.5；纯标题猜测 0.3。最高一档，不按来源次数加分。
- `sessionPositive`：当前会话显式认可为 1、可靠有效收听为 0.7、无正反馈为 0。`repeatPenalty` 上限 0.25（2 小时之后按 24 小时半衰期减弱），`contextNegativePenalty` 上限 0.25（not_now 在 24 小时后清零）。所有最终分数限制在 0–1。

以上数值是待对照验证的初始启发式，不是训练结果。来源置信度只衡量相关证据，不能替代硬约束所需的具体字段证据。

### 7.4 模型选曲与最终排序

模型收到候选：ID、上游歌名/歌手、阶段匹配、可靠标签、熟悉类别、来源证据、基础得分摘要。输出仅允许 `selected:[{trackId,stageId,reasonEvidenceIds}]` 和可选的有限补查 actions。

候选证据统一为 `{id,kind,value,source,confidence}`；evidenceId 在一次推荐内唯一。模型只引用这些 ID，最终中文短理由由已验证证据生成；禁止仅因“收藏”解释出具体乐器、歌词或创作背景。

校验：ID 全部属于本轮候选集、无重复、数量正确、阶段存在、证据引用合法。禁止模型新写歌名再作为结果；无效部分丢弃，用确定性基线补位，不能让整个请求反复重跑。

程序进行最后的多样性编排：默认同一主歌手不相邻、每连续 6 首同一主歌手最多 2 首、同专辑最多 2 首；种子来源尽量分散。明确歌手/专辑专题可覆盖对应限制。少数歌手的曲库可放宽，但必须记录；不能为了多样性放进不合题的歌。

多阶段先按实际曲长分配，再在阶段内兼顾相邻探索；不再只有收藏才能分阶段。已知曲长时目标误差不超过 `max(3 分钟, 该阶段最长一首歌时长)`；若 30 首上限或硬约束导致不可达，报告实际阶段时长和缺口。未知时长曲目不能用于承诺时长覆盖。没有音频能量证据时，只能说按场景/风格过渡，不承诺真实能量曲线或无缝衔接。

## 8. 播放资格与降级

`PlayabilityService` 输出：`full / preview / blocked / unknown`、`checkedAt`、`reasonCode`、可用时长与上游证据摘要。保留试听、权限等字段；不能只用 URL 是否存在判断 full。字段缺失但有 URL 时，用已验证的返回契约和时长证据判断；证据仍不足则 unknown，不能假设完整。

最终推荐仅交付 full；用户主动搜索的试听展示策略可沿用现有行为，但不能混入“完整电台”。音频代理继续在实际播放时取得新 URL；生成时可播不代表永久可播。权限/登录失效要作为全局来源状态呈现，不把整库逐首记成用户不喜欢。

默认资格缓存：full 10 分钟、blocked/preview 2 分钟；timeout/unknown 最多 30 秒，网络失败不能持久化为版权受限。缓存按账号隔离，只保存资格及时间，日志不保存签名播放 URL。实际播放失败触发资格重查一次，仍失败向前端说明并按当前播放模式处理，不无限跳歌。

降级顺序：Agent 重排失败 -> 确定性排名；单路召回失败 -> 其余合规来源；探索不足 -> 降低软配额并说明；完整候选不足 -> 返回较少歌曲和原因。0 首合格时不替换队列、不创建成功电台历史、不声称“已安排”。即便不足默认 24 首，也不为凑数引入 blocked/preview 或违背硬约束的歌。

主持人文案只能使用已选定歌曲和有来源事实；歌词时间戳空白不等于已验证无人声。无事实时可表达场景建议，不编创作背景。选歌核心完成后先确定可交付结果，TTS/评论/串词失败不让推荐整体失败；首版允许该期无解说，沿用当前前端兼容结构，不为语音引入新的长任务 API。

## 9. 反馈闭环：事件与学习规则

### 9.1 最小事件协议

新增 `POST /api/listening/events`，支持最多 50 条批量。单条含：

```json
{
  "schemaVersion": 1,
  "eventId": "唯一且重试不变的ID",
  "accountKey": "服务端绑定",
  "playbackSessionId": "每次加载/重新起播一首歌的新会话",
  "seq": 4,
  "loopIndex": 0,
  "recommendationId": "来源推荐ID；手动播放可为null",
  "trackId": "真实歌曲ID",
  "type": "progress",
  "positionMs": 60000,
  "listenedMs": 55000,
  "coveredRangesMs": [[0, 25000], [30000, 60000]],
  "durationMs": 240000,
  "reason": null,
  "occurredAt": "客户端ISO时间",
  "context": {"stageId": "focus-1", "scene": "focus", "source": "radio"}
}
```

账号由服务端解析，不信任客户端账号参数；场景在实际开始播放时绑定对应推荐/阶段，不能从全局最后生成的 `state.now` 推断。每轮单曲循环可沿用会话并增加 loopIndex，学习时按歌曲/会话去重和限幅。暂停恢复不新建会话，不重复增加正反馈。

实现补充：`undo_not_now` 用于按 `undoOf` 事件 ID 撤销本次场景反馈；不会清空此前独立反馈。

事件类型：`exposure`（仅实际展示的推荐）、`play_start`（实际 playing 后一次）、`progress`、`complete`、`skip`、`like`、`unlike`、`dislike`、`undo_dislike`、`not_now`、`queue_remove`、`play_error`。终止会话可以先补传最后 progress；推荐生成但未展示不是 exposure，展示但未播放不是收听。

### 9.2 初始解释规则

| 信号 | 初始影响 |
|---|---|
| `like` | 强正反馈；重复点击幂等；仅本地喜欢，未经用户要求不写网易云 |
| `unlike` | 撤销对应应用内喜欢加分；不自动转为不喜欢；不移除网易云收藏证据 |
| `dislike` | 该曲显式屏蔽，直到撤销；不自动屏蔽整个歌手/曲风 |
| `not_now` | 当前场景中该曲临时降权；默认 24 小时衰减到零，不删除长期喜欢 |
| `queue_remove` | 队列整理，学习权重为 0 |
| `play_start`、暂停/恢复 | 学习权重为 0 |
| `skip` 且实际已听 < 20 秒、覆盖 < 35% | 仅当前歌曲/场景弱负反馈；显式 reason=不喜欢时才转 dislike |
| 有效收听覆盖 ≥ 70% | 每个会话一次弱正反馈；持续收听不是强喜欢 |
| `complete` | 仅在有效覆盖 ≥ 90% 时增加完成证据，替代而不叠加本会话 70% 奖励 |
| `play_error`、断网、加载失败、替换队列、自然结束 | 不产生负反馈 |

有效收听覆盖按实际播放的不同时间段合并长度 / duration 计算；进度拖动不增加已听时长，重复循环的累计秒数不冒充首次覆盖。客户端在 playing 状态按单调时钟记录时间段，排除 pause/waiting/stalled/seek，约 15 秒批量上报并在离开/终止时补发；后台上报不保证实时，服务端依据受限会话快照可延迟聚合。

服务端校验 ID、时间范围、单次增长上限、事件顺序与幂等。乱序快照不能让累计状态倒退；派生权重按会话最终状态重算，不是每收到 progress 加一次分。无可靠时长/覆盖时只保留原始事件，不奖励听完。页面关闭导致缺终止事件不自动当跳过。手动点击另一首也记录切换原因，但普通切换默认中性，不推断厌恶。

`seq` 在播放会话内递增；progress 发送累计 `listenedMs` 与已合并的 `coveredRangesMs` 快照。区间最多 64 段，超过后只保留可证明的覆盖，不把未听区间填满；服务端校验区间合法且总长度不超过可信收听秒数/歌曲时长。样例中“实际听了 55 秒、覆盖 55 秒”与跳过 5 秒相符。显式 like/dislike 可发生在尚未播放的卡片上，此时 playbackSessionId 允许 null，使用 eventId 和独立客户端 actionSeq 去重/排序，不伪造一次播放会话。

歌手/标签级偏好至少需要 3 首不同歌曲的同向可靠证据，使用有上限的平滑更新；不能因为跳过一首爵士就厌恶爵士。长期隐式偏好按 30 天半衰期衰减；显式收藏/喜欢不随之自动消失。每次推荐记录使用的画像版本以便重放。

### 9.3 持久化和旧数据迁移

- 继续使用本地文件：画像/缓存快照 + `data/listening-events/YYYY-MM-DD.jsonl` + 派生反馈快照，均在被忽略的 data 下。
- 事件 append 串行化，eventId 去重；重启重建索引，部分尾行可隔离修复。原始事件默认保留 90 天，压缩聚合含 provenance；明确屏蔽/撤销记录单独保留，不能随轮转丢失。
- 状态更新通过统一的 read-modify-write 互斥入口，禁止长时间模型调用持有写锁；生成结束以最新状态合并增量，不回写旧的队列/反馈快照。
- 迁移前备份，写 schemaVersion，可重复执行；明确喜欢与明确 dislike 可保留；旧 `remove/skip/play` 只作低可信历史，不转为新的强标签。旧 scenePreferences 中混合计数不直接继承为 V2 学习权重。
- 不删除旧字段，V1 回滚可读；V2 事件只由 V2 聚合计算，禁止旧 taste 与新事件两路重复学习。兼容 `/api/taste` 的旧客户端请求可记录 legacy，不再自动视为可靠强反馈。

## 10. 接口、可观测性与兼容

### 10.1 对现有接口的增量

- `/api/chat` 与 `/api/chat/stream` 保持现有 `tracks`、`assistantText`、`plan`、`radioHistoryItem` 和 NDJSON result 事件，新增 `recommendationId`、`algorithmVersion`、`degraded`、`warnings`、`selectionSummary`。卡片、替换、追加各自遵守队列动作契约。
- 推荐曲目新增 `recommendationId`、`stageId`、`reasonSummary`、`evidenceIds`、`familiarity`、`playability`。这些字段必须经过队列持久化、刷新与电台历史往返，不被 `normalizeQueueTrack` 丢弃。手动搜索歌曲字段可缺省。
- 新增本地 `POST /api/profile/sync`、`GET /api/profile/status`。启动同步返回任务状态，轮询 status 即可，不把整库同步塞进单个长 HTTP 请求。
- 新增 `POST /api/listening/events`；返回已接受/重复/拒绝的 eventId，网络失败可重试且不阻断播放。
- 新增 `GET /api/recommendations/:id/explanation?trackId=...`，按真实 trace 给出短解释，不调用新检索；找不到历史时诚实说明。

最小界面改动：复用喜欢/取消喜欢；曲目更多菜单增加“现在不合适”“不喜欢”“为什么推荐”，负反馈后可撤销。“删除”仍只整理队列。无需增加复杂参数面板，探索模式优先从自然语言识别。

队列操作保留 200 首上限与现有去重规则。append 不移走或打断当前播放，满额只接受剩余空间并说明；cards 不自动入队。请求携带 requestId 和 expectedQueueRevision，服务端/前端都拒绝过期响应自动替换：生成期间用户已修改队列时，结果仍可作为卡片交付，但不得覆盖新队列。V2 生成推荐不写“正在播放”状态，只有实际 playbackSession 的开始/切换更新它；生成记录与实际播放状态分离。

`selectionSummary` 至少含 requested/returned 数量、实际时长、各阶段覆盖、已知熟悉/探索/未知数量、来源状态、配额放宽原因。正常界面只呈现简短有用的信息；完整 trace 留在本地调试，不能把技术标签塞进主播台词。

### 10.2 Trace 与评测日志

本地 trace 记录：requestId、算法/策略版本、画像版本、随机种子、结构化意图、工具动作/状态/耗时、候选来源、拒绝原因、分数分解、模型选中 ID、回退原因、最终资格、数量/时长缺口。建议每请求一份 JSON，保留 30 天。

不记录模型隐藏推理；只保存结构化决策和证据。密钥、Cookie、账号原始资料、签名音频 URL 不进 trace。真实用户请求与偏好只存本地被忽略目录，测试夹具使用合成/脱敏数据。

配置 `RECOMMENDER_VERSION=v1|v2`，开发期间默认 v1；联调验收后切 v2。保留 `RECOMMENDER_AGENT_RERANK=false`，可单独关闭模型重排来定位问题。固定 now/seed/工具快照即可离线重放确定性部分；模型对照保存其结构化输出，不宣称温度为 0 就完全可复现。

## 12. 测试与验收

### 12.1 离线测试（不得调用真实模型或网易云）

构建至少 40 个固定请求，覆盖场景、探索、严格主题、精确点歌、多阶段、控制/聊天、冲突、冷启动；使用真实结构的合成歌曲和 stub 工具响应。断言行为与约束，不把某次模型输出的歌曲顺序写死成正确答案。

必须覆盖：

1. 收藏缺失/同步一半/跨页失败/空库/记录接口无权限；不覆盖成功快照，不错误声称零播放。
2. 不同歌曲同名不误杀；同曲版本收敛；明确 Live/专辑专题覆盖默认多样性规则。
3. 否定、数字、歌手限制、未知语言/人声不能被模型或补位放宽。
4. 候选重复来源合并、类别互斥、探索不足可说明；没有播放证据不说“你没听过”。
5. 模型 JSON 非法、未知 ID、重复 ID、越权工具、参数超限；一次修复耗尽后确定性回退。
6. 歌单简介/评论包含“忽略指令/访问某 URL”不触发额外工具。
7. 试听 URL、不齐批量返回、ID 乱序、资格过期、401/301/429/timeout 和 HTTP 200 业务失败。
8. 自然结束、单曲循环、拖到结尾、暂停恢复、跳过、切歌、删除、取消喜欢、断网；不重复学习、不误判厌恶。
9. 事件重复/乱序/重启、反馈撤销、日志尾行不完整；连续与分批上报的派生偏好一致。
10. 生成期间点喜欢/改队列、连续两个推荐请求、取消请求；旧结果不覆盖新状态。
11. 不足 24 首、0 首、数量与时长冲突、阶段时长不可达；不得虚报成功和覆盖。
12. V1/V2 切换、队列/电台历史序列化保留推荐归因、旧客户端兼容，以及现有 8 个界面逻辑测试。

工程门槛：最终 ID 可追溯率 100%，硬约束违反 0，重复 ID 0，明确试听/受限混入 0，模型工具越界 0，重复事件导致权重变化 0。相同 fixture 的约束检查必须可重复通过。

### 12.2 联调与连续收听（不能用 mock 代替）

用当前用户自己的账号验证收藏分页、日推、相似、搜索、歌手专题和主题歌单；仅将实际成功的来源标为可用。记录 business code/结构，不输出凭证。不生成整库音频探测流量。

至少验证 6 类真实请求：熟歌、探索、纯音乐/排除版本、歌手加指定歌曲、多阶段、空/不足候选；再做一次不少于 30 分钟的本地连续收听，检查实际播放、切歌、解说失败与反馈归因。用户的真实喜欢/不喜欢不得为测试自动覆盖。

性能目标（须实测报告）：已缓存画像条件下，普通 5 首请求 p95 ≤ 15 秒；24 首整期选歌阶段 p95 ≤ 30 秒；TTS 不计入选歌但单独报告耗时。未达到时报告瓶颈，不能靠隐藏资格校验或偷偷缩短结果达标。

### 12.3 体验对照与上线决策

- 使用相同请求、画像快照和工具快照，比较 V1、V2 确定性内核、V2+Agent 三组；分别记录配额、重复、约束、延迟和费用/调用次数。
- 选至少 10 组真实需求，让用户不知版本地比较“贴合这次要求 / 想继续听 / 有合适的新发现 / 顺序舒服”各 1–5 分。小样本只作个人产品决策，不宣称统计显著。
- 播放漏斗分别计曝光、实际起播、有效覆盖、早跳过、明确喜欢；曝光未播放不能放进“听完率”分母。探索接受率只统计确实起播的探索曲目，不用加入队列代替认可。
- 默认启用条件：工程门槛全过；真实接口和连续播放验收完成；10 组对照中至少 7 组整体更偏好 V2，且贴合要求无明显退步。若 Agent 没胜过确定性内核，可以先启用 V2 内核、保留 Agent 重排关闭，并记录结论。
